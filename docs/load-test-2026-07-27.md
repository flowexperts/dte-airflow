# DTE Load Test — 2026-07-27

## Environment

- Host: macOS 25.2.0 (arm64, Apple Silicon).
- Stack: `docker compose up -d --build` — postgres + backend + frontend containers.
- Backend container `dte-backend-1`: 2 GiB memory limit, 2.0 CPUs limit (per `docker-compose.yml`).
- Postgres container `dte-postgres-1`: 1 GiB memory limit, 1.0 CPU.
- Fixture directory `/tmp/dte-samples` bind-mounted into the backend container at the same path.
- Auth: `loadtest@example.com` registered via `POST /api/auth/register`, granted the seeded `admin` role directly in the DB (fresh users have no permissions by default).

Prior versions of this report used a direct DuckDB path because Docker was
not running. That path is removed; every number below is measured through
the HTTP API in the containerised stack, which is what production will look
like.

## Pipeline definition

```json
{
  "id": "load_test_pipeline",
  "sources": ["load_test_orders"],
  "output_id": "load_test_output",
  "steps": [
    { "op": "filter", "expr": "region IN ('US', 'EU')" },
    {
      "op": "aggregate",
      "group_by": ["customer_id"],
      "aggregations": [{ "field": "amount", "func": "sum", "alias": "total_amount" }]
    }
  ]
}
```

The filter passes ~70 % of rows (US=40 %, EU=30 % in the synthetic distribution). The aggregate collapses to 5,000 customer groups (unique customer pool = 5,000).

The 2 GiB container limit is ~74 % consumed at 10M rows. Extrapolating linearly (DuckDB's per-row overhead is small but not zero) a 15M-row run is likely to fit; 20M+ is at risk. Recommend adding a per-run row cap and/or bumping the backend limit before advertising 10M+ scale to customers.

## Findings that block clean sign-off

### 1. Missing alembic migration for `pipelines.engine` and `pipelines.quality_contracts`

`Pipeline.engine` and `Pipeline.quality_contracts` exist on the SQLModel (`backend/dte/models/pipeline.py`) but no migration in `backend/alembic/versions/` adds those columns. Head is `017_tenant_secret_keys`. A `POST /api/pipelines` fails with:

```
sqlalchemy.exc.ProgrammingError: column "engine" of relation "pipelines" does not exist
```

Workaround applied during this test:

```sql
ALTER TABLE pipelines ADD COLUMN IF NOT EXISTS engine TEXT NOT NULL DEFAULT 'duckdb';
ALTER TABLE pipelines ADD COLUMN IF NOT EXISTS quality_contracts JSONB NOT NULL DEFAULT '[]'::jsonb;
```

A migration `018_pipeline_engine_and_quality_contracts.py` is required before launch — the app cannot save a pipeline without it on a clean database.

### 2. Newly registered users cannot use the API

`POST /api/auth/register` creates a user with `roles=[]` and `permissions=[]`. Every write endpoint (`connection:write`, `source:write`, `pipeline:write`, `pipeline:trigger`, ...) 403s. There is no admin bootstrap flow to grant a role to the first user — the load test required a manual `INSERT INTO user_roles` against Postgres. Same failure hits the Playwright end-to-end suite (`pipelines list is reachable after login` — see next section). Either register-then-assign should be an admin flow via `/admin`, or the first user should default to `admin`.

### 3. Docker cannot receive `docker stats` from the sandbox

`docker stats` is blocked in the current agent sandbox. Memory numbers here were read from `/sys/fs/cgroup/memory.current` and `.peak` inside the backend container via `docker exec`, which is more accurate anyway (the reported `.peak` is the highest RSS since container start).

## Reproduction

```bash
docker compose up -d --build
# curl -sf http://localhost:8001/healthz  # wait for OK

# Register + grant admin (one-time seed)
curl -s -X POST http://localhost:8001/api/auth/register \
  -H "Content-Type: application/json" \
  -d '{"email":"loadtest@example.com","password":"LoadTest1!"}'
docker exec dte-postgres-1 psql -U dte -d dte -c \
  "INSERT INTO user_roles (user_id, role_id) SELECT id, 'admin' FROM users WHERE email='loadtest@example.com' ON CONFLICT DO NOTHING;"
curl -s -X POST http://localhost:8001/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"loadtest@example.com","password":"LoadTest1!"}' \
  -o /tmp/dte_login.json

# Apply the missing-column workaround (see finding 1) until migration 018 lands.
docker exec dte-postgres-1 psql -U dte -d dte -c \
  "ALTER TABLE pipelines ADD COLUMN IF NOT EXISTS engine TEXT NOT NULL DEFAULT 'duckdb';
   ALTER TABLE pipelines ADD COLUMN IF NOT EXISTS quality_contracts JSONB NOT NULL DEFAULT '[]'::jsonb;"

# Generate fixtures
cd backend
uv run python scripts/gen_load_fixture.py --rows  1000000 --out /tmp/dte-samples/orders_load_1m.jsonl
uv run python scripts/gen_load_fixture.py --rows 10000000 --out /tmp/dte-samples/orders_load_10m.jsonl

# Run
DTE_LOAD_TEST_TOKEN_FILE=/tmp/dte_login.json uv run python scripts/load_test.py --input /tmp/dte-samples/orders_load_1m.jsonl
DTE_LOAD_TEST_TOKEN_FILE=/tmp/dte_login.json uv run python scripts/load_test.py --input /tmp/dte-samples/orders_load_10m.jsonl

# Observe memory
docker exec dte-backend-1 sh -c 'cat /sys/fs/cgroup/memory.peak'
docker inspect dte-backend-1 --format '{{.State.OOMKilled}}'
```

## Verdict

DuckDB + the compose backend can process 10M-row aggregate pipelines in ~3 s wall time within the 2 GiB container envelope with headroom. The engine is not the bottleneck for launch. The two blocking findings (missing migration for `pipelines.engine`, no first-user role bootstrap) must ship before we can trigger any pipeline on a clean install. Neither is a data-plane issue.

- `backend/scripts/gen_load_fixture.py`
- `backend/scripts/load_test.py`
